구조 설명

이 프로그램이 어떤 조각으로 이루어져 있고, 테이블 하나를 옮길 때 무엇이 어떤 순서로 움직이는지

1. 한 문장으로

소스 DB 의 테이블을 Reader 가 페이지 단위로 읽고, Processor 가 타겟 모양으로 바꾸고, Writer 가 묶어서 적재합니다. 이 셋을 테이블마다 하나씩 만들고, 업무 단위로 Strategy · Plugin 이 묶습니다. 실행·안전장치·기록(게이트, 실행 전 확인, 채번, 청크 추적, 이력, 알림)은 core 가 공통으로 맡고, 개발자는 Source SQL · Processor 몇 줄 · Target SQL 만 씁니다.

제품 원칙: 타겟 데이터를 지우지 않는다 · 시스템 전체에서 한 번에 하나만 실행한다 · 실행·중단·정리는 사람이 화면에서 한다.

3. 테이블 하나가 옮겨지는 순서

#누가무엇을보이는 곳
1테이블 이관 실행 화면 / API플러그인 · 테이블 · 모드 · 테넌트 · 청크 크기를 담은 요청을 보낸다. 실행자 이름은 헤더 X-Executed-By 로.테이블 이관 실행 → 요청 미리보기
2ExecutionGate다른 이관이 돌고 있으면 409 로 거절. 아니면 실행 단위를 잡는다.실행 현황 → 실행 게이트, 상단 배너
3PreRunGuardServiceNORMAL 이면: 시퀀스 정책 확인 → 미완 코드(원천 미지정) 차단 → 타겟 기존 데이터 있으면 경고 후 중단(ignoreExistingData 면 진행) → 실행 전 점검(설정 시).차단 패널 · 알림
4Strategy테이블의 Reader · Processor · Writer bean 을 찾아 Spring Batch Job 을 만들고 띄운다. 청크 크기·TableOptions(채번 컬럼 등) 를 JobParameters 에 싣는다.로그 "Starting optimized table migration"
5Reader총 건수를 세고(selectTotalCount) 페이지 단위로 SELECT(selectPageData). 기간·테넌트 조건은 SQL 에 바인딩.진행 현황의 소스 건수
6Processor행마다 validateItem(필수값) → transformItem(TargetDto 로 옮겨 담기, 코드·경로 변환) → 채번 컬럼에 번호 부여 → setUpdateTimestamp(감사 컬럼 기본값). 실패한 행은 기록하고 계속.진행 현황 · 실패 건수 · 시퀀스 요약
7Writer청크를 큐에 모아 배치 INSERT. 큐 플러시 정책과 적재 대기 시간을 지킨다. UPSERT 여부는 Target XML 이 정한다.진행 현황의 적재 건수 · 청크 상세
8리스너청크마다 migration_chunk_status 기록, Job 끝에 시퀀스 MAX 동기화(SequenceSyncJobListener), 완료 판정(실패·경고), 알림(텔레그램·UI).이력 상세 · 알림
테스트 모드는 이 순서를 중간에서 멈춥니다. READER_TEST 는 5단계까지(기본 5건), PROCESSOR_TEST 는 6단계까지(적재 없음), WRITER_TEST 는 7단계를 100건만(등록자 MIG-TEST). NORMAL 이 전량입니다.

Reader common/reader/AbstractPagingItemReader

소스 매퍼(Source XML)를 페이지 단위로 호출해 SourceDto 를 내보냅니다. 생성기가 만든 그대로 쓰는 것이 보통이고, 개발자가 손대는 곳은 Source 매퍼 XML 의 SELECT 입니다.

메서드역할
getTotalCount()소스 건수 (진행률 분모). selectTotalCount
getPageData(offset, limit)한 페이지 SELECT. selectPageData + OFFSET/FETCH
createFilterParams()테넌트 5단계 · 기간(startDate/endDate) · attribute1~25 를 SQL 파라미터로
규칙: SELECT 별칭은 TOBE 컬럼명(대문자) · 날짜는 TO_CHAR 로 14/8자리 문자 · 삭제건은 WHERE 로 제외 · 정렬키는 유일해야 페이징이 맞음 · 채번 받을 컬럼은 NULL AS "FILE_ID". 원천이 아직 없는 테이블은 WHERE 1 = 0 으로 두면 실행이 차단됩니다.
기본은 엔진의 SqlPagingReader 가 Source XML(selectTotalCount·selectPageData)을 부릅니다. 특수한 테이블만 TableDef.reader(…) 로 직접 만든 Reader 를 붙입니다.

Processor common/processor/AbstractItemProcessor<I, O>

SourceDto 한 행을 TargetDto 로 옮깁니다. SQL 에서 못 하는 Java 후처리(코드표 변환, 경로 치환, 필수값 검증, 감사 컬럼)만 여기서 합니다. 행마다 DB 를 조회하지 않습니다.

메서드역할
validateItem(item)NOT NULL · 형식 검증. 실패는 행 단위로 기록하고 Job 은 계속
transformItem(item)TargetDto.builder()…build(). 코드 변환은 업체 CodeRules, 경로는 PathRules, 타입은 ConvertUtils
getItemId / getOutputItemId로그·실패 기록용 식별자 (ASIS 키 / 채번된 키)
setUpdateTimestamp(out)INDATE·LDATE·INUSERID·LUSERID 비어 있으면 MIG-DATA · 현재 시각
applySequences (core)TableOptions.sequenceColumns 에 적힌 컬럼이 NULL 이면 번호 부여 (블록 선점 v1)
같은 이름 컬럼만 옮기면 Processor 없이 엔진의 CopyProcessor. 도구 "DDL → Processor" 가 초안을 만듭니다.

Writer common/writer/AbstractBatchMigrationWriter → AbstractMigrationWriter · queue/QueueingItemWriter

TargetDto 를 큐에 모아 배치 INSERT 합니다. 트랜잭션·플러시·대기 시간·실패 집계는 core 가 하고, 개발자는 Target 매퍼 XML 의 INSERT 문 만 씁니다.

메서드역할
insertItem(session, item)session.getMapper(XxxTargetMapper.class).insertData(item)
getItemId(item)실패 행 식별자 (TOBE PK)
적재 방식은 Target XML 이 정합니다: 일반 INSERT(기본, 기존 데이터 있으면 차단) · INSERT IGNORE · ON DUPLICATE KEY UPDATE(UPSERT, 재실행은 ignoreExistingData=true). 제품은 TRUNCATE·DELETE 를 하지 않습니다.
기본은 엔진의 SqlBatchWriter 가 Target XML 의 insertData 를 부릅니다. upsert·후처리가 필요하면 TableDef.writer(…). 도구 "DDL → Writer"

SourceDto · TargetDto plugins/<업체>/source/dto · target/dto

둘 다 Lombok @Data @Builder 클래스입니다. SourceDto 는 Reader 출력이자 Processor 입력이며, Source SQL 이 TOBE 컬럼명으로 별칭을 주므로 필드도 TOBE 이름입니다(ASIS 값을 TOBE 타입으로 바꾼 값). TargetDto 는 Writer 입력으로 TOBE 테이블 정의와 1:1 입니다.

타입 규칙: NUMBER(p,0) p≤9 Integer · ≤18 Long · 그 외 BigDecimal, DATE → LocalDateTime(SQL 에서 문자로 바꿨으면 String), CLOB → String, RAW/BLOB → byte[]. MySQL INT → Integer, BIGINT → Long.
도구 "DDL → 자바 모델" 이 같은 규칙으로 만듭니다.

Strategy · Plugin · TableOptions core/strategy/AbstractTableMigrationStrategy · core/spi/DomainPlugin

Strategy 는 업무(플러그인) 하나가 지원하는 테이블 목록과 테이블별 옵션을 알고, 요청이 오면 그 테이블의 Reader·Processor·Writer 로 Job 을 만들어 실행합니다. 업무는 @GeoruPlugin 카탈로그 클래스 하나에 TableDef 목록으로 선언하고(이름 예: hr.board), 엔진(GeoruPluginRegistrar)이 Strategy·Plugin 과 테이블별 Reader·Writer 를 만듭니다.

TableOptions뜻
sequenceColumns새 번호를 받을 컬럼 (Source 는 NULL 을 내야 함)
sequenceSync / sequenceSyncColumnsJob 끝에 관리 테이블 현재값을 MAX 로 동기화. 번호를 유지하는 PK 는 동기화만
ignoreExistingData테이블 기본값. 요청 값이 우선
targetTableJob 키와 타겟 테이블명이 다를 때만
테이블별 채번·건수 비교 같은 옵션은 TableDef.options(TableOptions…). 플러그인 토글 georu.plugins.<name>.enabled.

ExecutionGate core/gate

시스템 전체에서 이관 단위 하나만 실행되게 합니다. 실행 중이면 새 요청은 409 EXECUTION_BUSY, 스케줄은 건너뜁니다. 실행 목록은 게이트가 비기를 기다렸다가 다음 테이블을 보냅니다. GET /api/migrate/gate, 수동 해제 POST /api/migrate/gate/release. 같은 테이블을 이관과 점검이 동시에 쓰지 못하게 TableUsageRegistry 가 막습니다.

PreRunGuardService · PrecheckService core/product/guard · core/product/precheck

실행 전 확인: 이관 상태(대기 · 제외면 차단, 모든 모드) → 사용 중 · 시퀀스 정책 · 미완 코드(원천 미지정) 차단(모든 모드) → 타겟 기존 데이터 있으면 경고 후 중단(NORMAL) → 실행 전 점검(NORMAL, 설정 georu.precheck.auto-enabled). 실행 전 점검은 소스 샘플을 Processor 까지 돌려 타겟 컬럼 정의(길이·NOT NULL·타입·PK 중복)와 대조합니다. INSERT 문은 MyBatis 로 문장만 만들고 실행하지 않습니다. 화면 /ui/precheck 에서 단독으로도 돌리며, 타겟 점검 · 소스(ASIS) 점검을 나눠 돌릴 수 있습니다.

알려진 한계: 타겟 스키마가 접속 기본 DB 와 다르면 기존 데이터·점검·동기화가 빗나감 (접속 기본 DB 를 타겟 스키마로 맞춰 해결).

시퀀스(채번) core/sequence

관리 테이블(기본 mig_sequence, 설정으로 변경; TABLES/COL/SEQ) 에 테이블·컬럼별 현재값을 둡니다. Processor 가 블록(1000) 단위로 선점해 번호를 주고(번호 공백 허용), Job 끝에 MAX 로 동기화합니다. 테스트 모드는 DRY_RUN. ASIS 시퀀스 현재값을 먼저 이 테이블로 옮기는 것이 첫 단계. API /api/v1/sequence.

리스너 · 완료 판정 · 알림 core/listener · core/sequence/SequenceSyncJobListener · core/product/verdict · core/product/notice

MigrationJobListener 가 Job 시작·종료를 migration_jobs 에, MigrationChunkListener 가 청크마다 진행률을 migration_chunk_status 에 기록합니다. SequenceSyncJobListener 는 Job 끝에 MAX 동기화, MigrationVerdictListener 는 실패·경고를 판정, ProductNotifier 가 텔레그램과 UI 알림으로 같은 내용을 보냅니다.

업체 규칙 유틸 · 미완 코드 plugins/<업체>/utils · core/utils/rule · core/product/mapping

코드표·경로·감사 규칙은 업체 패키지의 CodeRuleSet · PathRuleSet · AuditRuleSet 구현에 두고 Processor 가 부릅니다. 범용 유틸(core.utils)은 업체를 모릅니다(ArchUnit 이 지킴). MappingStatusService 는 XML·Processor 의 TODO 와 WHERE 1 = 0 을 세어 테이블 이관 실행 화면의 "미완 코드 현황"에 보여 주고, 검토가 끝난 줄은 주석 @mig-ok: 사유 로 제외합니다.

데이터소스 georu.datasource.* · GeoruDataSourceRegistrar

DataSource 는 이름으로 선언합니다: 운영 저장소 operation, 소스 source-m·source-1…, 타겟 target-m·target-1…. 이름마다 DataSource·SqlSessionFactory·TransactionManager 가 만들어집니다. 플러그인은 @GeoruPlugin(source, target) 으로 쓸 DataSource 를 고르고, 매퍼 인터페이스 없이 XML namespace 로 호출합니다. 데이터소스 토글과 플러그인 토글의 조합이 어긋나면 기동 시 한 줄로 실패합니다.

운영저장소 core/operation

Spring Batch 메타(BATCH_*)와 제품 테이블(migration_jobs · migration_logs · migration_chunk_status · 점검 결과 · 알림 · 시스템 지표) 을 H2 파일(기본) 또는 MySQL 에 둡니다. 이력·보고서·대시보드가 모두 여기서 읽습니다. 로컬은 TCP 9092 로 DBeaver 접속.

입구 ui/UiPageController · api/controller/MigrationExecutionController · core/scheduler

운영 UI(/ui) 는 로그인 없이 같은 서버의 /api/** 를 부릅니다. 테이블 이관 실행 폼은 POST /api/migrate/table 본문과 1:1 이라 JSON 붙여넣기·복사가 됩니다. Cron 은 스케줄로 등록돼 실행 현황에서 관리합니다.

도구 · 생성기 · 예제 /ui/ddl*

테이블 하나에 사람이 쓰는 파일은 Source XML · Target XML · Processor 3개이고, DTO 2개는 도구가 만듭니다. 같은 이름 컬럼은 자동 매핑, 다른 것은 TODO 로 남깁니다. 도구 메뉴의 DDL 페이지들은 DDL 만으로 DTO·Processor·Writer 초안을 브라우저에서 만듭니다. 앱이 예제 안내서를 더했다면 안내서 메뉴에 함께 보입니다.
